# Развёртывание OG.Listener

Интерфейс размещается на GitHub Pages, а API - на Vercel. Архив Spotify разбирается в браузере; API ищет публичные метаданные и внешние ссылки на медиа. Пользователю сайта не нужны установка приложения или ключи поставщиков.

## Структура репозитория

В корне репозитория должны находиться `package.json`, `vercel.json`, `.github/`, `api/`, `server/` и `src/`. Если рабочий проект находится в папке `site`, публикуйте содержимое этой папки как корень репозитория. Workflow GitHub Pages рассчитан именно на эту структуру.

Сохраняйте `package-lock.json`, тесты, скрипты сборки и оба workflow: они нужны для воспроизводимой установки и проверок. `node_modules/`, `dist/`, `.vercel-static/`, локальные ключи и личные архивы исключены через [`.gitignore`](../.gitignore).

## 1. API на Vercel

Импортируйте GitHub-репозиторий в Vercel и настройте проект:

| Параметр | Значение |
| --- | --- |
| Framework Preset | Other |
| Node.js | 24.x |
| Root Directory | Каталог с `package.json` и `vercel.json`; при рекомендуемой структуре - корень репозитория |
| Build Command, Output Directory, Install Command | Оставьте конфигурацию из `vercel.json` |

[`vercel.json`](../vercel.json) запускает `node scripts/prepare-vercel.mjs` и публикует API через `api/index.js`. Скрипт создаёт в `.vercel-static` единственный `index.html` с минимальной страницей API и ссылкой на `/healthz`: Vercel не принимает пустой Output Directory. Интерфейс собирается отдельно для Pages; исходники, архивы и личные данные в этот каталог не копируются. Не заменяйте эту настройку на `npm run build` и `dist`. Серверная часть использует встроенные модули Node.js. Обычный шаг установки зависимостей пропускается; сборщик Node.js Function может отдельно установить зависимости из `package.json` при упаковке функции.

В Environment Variables для **Production** задайте:

| Переменная | Назначение |
| --- | --- |
| `CORS_ORIGINS` | Разрешённые адреса интерфейса, например `https://username.github.io` |
| `LASTFM_API_KEY` | Необязательные теги и жанры Last.fm |
| `JAMENDO_CLIENT_ID` | Необязательный дополнительный источник полных записей |
| `CHARTMETRIC_REFRESH_TOKEN` | Необязательный платный источник истории месячных слушателей |

Все имена и параметры ограничения запросов перечислены в [`.env.example`](../.env.example). Ключи остаются только на API; переменные с префиксом `VITE_` попадают в публичный код интерфейса. После изменения серверного окружения выполните новое развёртывание.

`CORS_ORIGINS` принимает точные origin через запятую: протокол, имя хоста и при необходимости порт. Для `https://username.github.io/OG.Listener/` укажите **`https://username.github.io`**. Для собственного домена укажите его фактический origin. Пути, завершающий `/`, маски `*`, параметры URL и данные авторизации не допускаются. Публичные адреса должны использовать HTTPS; HTTP разрешён только для локального loopback. Пустое значение разрешает только обращения с того же origin и не подходит для отдельного сайта на Pages.

Production-адрес API должен быть доступен посетителям **без входа в Vercel**. Если включена защита развёртывания, настройте её так, чтобы она не блокировала публичный production API; preview-развёртывания можно оставить защищёнными. Не помещайте токены обхода защиты в интерфейс. Успешный `OPTIONS` сам по себе не подтверждает доступность основного запроса.

После развёртывания сохраните постоянный production origin, например `https://your-api.vercel.app`. На `/` открывается минимальная страница API. Откройте `/healthz` в приватном окне: ожидается `{"ok":true}`. Именно этот запрос проверяет обработчик API; статическая страница на `/` не подтверждает его работу. Проверка здоровья не проверяет всех внешних поставщиков.

`HOST`, `PORT`, `API_ONLY` и `TRUST_PROXY` для Vercel не нужны: платформа вызывает функцию напрямую. Адаптер использует проверенный IP из заголовка платформы только в окружении Vercel.

Если сборка завершается с `[invalid_function_runtime] Function Runtimes must have a valid version`, проверьте, что в `functions["api/index.js"]` нет `runtime: "nodejs22.x"` или аналогичного значения. Встроенный Node.js runtime определяется по файлу функции автоматически; поле `runtime` в этой конфигурации предназначено для пользовательских runtime-пакетов. Версию Node.js выбирайте в Settings → Build and Deployment → Node.js Version с учётом `engines.node` в `package.json`, как описано в [документации Vercel](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions).

При `[STATIC_BUILD_EMPTY_OUT_DIR]` убедитесь, что разворачивается актуальный коммит со скриптом `prepare-vercel.mjs`, создающим `.vercel-static/index.html`, а Build Command и Output Directory соответствуют `vercel.json`. Пустая папка или файл `.gitkeep` не заменяют эту страницу.

## 2. Интерфейс на GitHub Pages

1. В GitHub откройте **Settings → Secrets and variables → Actions → Variables**. Создайте repository variable `VITE_API_BASE_URL` со значением production origin API, например `https://your-api.vercel.app`. Не добавляйте `/api`, другие пути, параметры или ключи.
2. В **Settings → Pages → Build and deployment → Source** выберите **GitHub Actions**.
3. Отправьте изменения в ветку `main` или вручную запустите workflow **Deploy OG.Listener to GitHub Pages** на вкладке Actions.

[`static.yml`](../.github/workflows/static.yml) устанавливает зависимости через `npm ci`, запускает тесты и `npm run build:pages`, затем публикует только `dist/`. Путь проекта получает из `configure-pages`; для обычного project Pages вручную менять его не нужно. Без корректного `VITE_API_BASE_URL` сборка Pages завершится ошибкой до публикации.

На Pages используется hash-навигация: `https://username.github.io/OG.Listener/#/upload`. Она поддерживает перезагрузку и переходы назад/вперёд без серверной переадресации SPA. При локальном запуске сохраняется маршрут `/upload`.

Адрес API встраивается в сборку: после изменения `VITE_API_BASE_URL` заново запустите Pages workflow. Если меняется домен интерфейса, обновите также `CORS_ORIGINS` на Vercel и повторите развёртывание API.

### Белый экран на Pages

В репозитории должен оставаться один workflow публикации интерфейса - `.github/workflows/static.yml` из этого проекта. Удалите старый `pages.yml`, если он остался: одинаковые группы `concurrency` могут отменять сборки друг друга. Не заменяйте содержимое `static.yml` стандартным шаблоном Static HTML, публикующим весь репозиторий без сборки Vite.

Проверьте, что **Settings → Pages → Source** установлен в **GitHub Actions**, переменная `VITE_API_BASE_URL` задана в **Actions → Variables**, а последний запуск именно `static.yml` успешно выполнил `Build frontend` и `deploy`. Если сборка завершилась ошибкой, старая версия сайта остаётся опубликованной; повторный деплой Vercel её не обновляет.

В исходном коде опубликованной страницы должны быть ссылки вида `/OG.Listener/assets/…js` и `/OG.Listener/assets/…css` (либо соответствующий путь вашего проекта). Ссылка `/src/main.jsx` означает публикацию исходников вместо содержимого `dist/`; на project Pages она приводит к 404 и не запускает приложение. Исправьте workflow и дождитесь успешной публикации, затем перезагрузите страницу.

## Проверка опубликованного сайта

1. Откройте загрузку архива на Pages и импортируйте свой ZIP или JSON.
2. Убедитесь, что статистика появилась, а после перезагрузки библиотека сохранилась.
3. Проверьте обложки и воспроизведение доступного аудио. В Network запросы `/api/…` должны идти на Vercel; ответы не должны подменяться страницей авторизации или блокироваться CORS.
4. Откройте сайт в отдельном профиле браузера: чужая библиотека там появляться не должна.

Если локальная статистика работает, а обложки и другие внешние данные отсутствуют, проверьте адрес API, production-защиту, `CORS_ORIGINS` и ответы поставщиков. Частичное отсутствие жанров, аудио или исторических слушателей возможно и при исправном API: покрытие каталогов ограничено.

## Ограничения и нагрузка

Vercel-конфигурация задаёт `maxDuration: 300` секунд, но запросы источников имеют собственные более короткие бюджеты. Допустимые ресурсы, длительность и стоимость нужно сверять с настройками проекта и условиями платформы; этот параметр не резервирует ресурсы и не гарантирует время ответа.

API принимает JSON до 1 МиБ для каталога и до 256 КиБ для истории аудитории. Ограничения проверяются для потока и уже разобранного платформой тела. Архивы и медиабайты через эти маршруты не передаются.

Кеши метаданных, объединение одинаковых запросов и ограничения нагрузки находятся в памяти **одного экземпляра** API. По умолчанию разрешены 12 активных запросов и 24 ожидающих, ожидание очереди - до 5 секунд. IP-ограничитель пополняет запас со скоростью 120 запросов в минуту и допускает всплеск до 30; хранится до 10 000 записей IP с ограниченным сроком жизни. При перегрузке API отвечает 429 с `Retry-After`. Настройки `API_*` описаны в `.env.example`.

Новый экземпляр Vercel начинает с пустыми кешами и собственными ограничителями. Эти настройки не являются общей квотой для всех экземпляров, защитой от любых расходов или доказательством работы на 10 000 одновременных посетителей. При росте нагрузки понадобятся измерения на опубликованном сервисе и, при необходимости, общий кеш и распределённый ограничитель запросов с учётом правил поставщиков.

Загрузка истории Kworb поддерживает продолжение между экземплярами: браузер хранит `archiveChecked` каждой записи массива `coverage` и передаёт только ограниченный список идентификаторов проверенных архивных снимков. Сервер сверяет их с настоящим индексом CDX и продолжает оставшуюся работу. Проверенные наблюдения объединяются в браузере; значения слушателей из клиента не принимаются как данные источника. Подробности - в [истории аудитории](audience-sources.md).

## Локальная работа

Требуется Node.js 22+; Node.js 24 соответствует настройке Vercel. Команды выполняются из корня проекта:

```sh
npm ci
npm run dev
```

Адрес разработки - `http://127.0.0.1:5173/upload`. В обычном режиме Vite подключает локальный API. Не задавайте внешний `VITE_API_BASE_URL`, если хотите использовать его.

Для проверки обычной production-сборки:

```sh
npm test
npm run build
npm start
```

Адрес - `http://127.0.0.1:3000/upload`. Необязательный `.env.local` задаёт серверные ключи; уже установленные переменные окружения имеют приоритет. `API_ONLY=true` запускает только API без `dist/`. `HOST` и `PORT` действуют только для этого локального сервера. `TRUST_PROXY` по умолчанию равен `none`; разрешены только точные IP доверенных прокси или `loopback`, `X-Forwarded-For` не используется.

Для локального просмотра именно Pages-сборки создайте игнорируемый `.env.pages.local`:

```dotenv
VITE_API_BASE_URL=https://your-api.vercel.app
VITE_BASE_PATH=/OG.Listener/
```

```sh
npm run build:pages
npm run preview -- --mode pages
```

Откройте `http://127.0.0.1:4173/OG.Listener/#/upload`. Для запросов к внешнему API временно добавьте `http://127.0.0.1:4173` в его `CORS_ORIGINS` и повторно разверните API. В Pages-режиме preview не запускает встроенный API.

## Данные и публикуемые файлы

Личная история сохраняется в IndexedDB текущего origin и профиля браузера. Автоматического срока удаления нет, но очистка браузерных данных удалит библиотеку. Между устройствами и доменами она не синхронизируется; повторная загрузка архива заменяет её. Сервер не хранит личную историю посетителей.

Обложки и аудио загружаются по внешним ссылкам. Приложение не создаёт локальные медиафайлы; обычный HTTP-кеш браузера и CDN может работать независимо.

GitHub Pages получает только `dist/`. Скрипт `check-public.mjs` проверяет разрешённое содержимое `public/`, а [`.vercelignore`](../.vercelignore) ограничивает набор отправляемых серверных файлов. Не помещайте личные архивы и ключи в публичные каталоги. При подключении стороннего мониторинга учитывайте, что тела запросов метаданных и query-параметры могут содержать названия музыки и даты первого прослушивания.
