# Предварительная загрузка метаданных

[English](en/preload-estimate.md)

Чтение архива и поиск внешних данных - разные этапы. Сейчас ZIP или JSON разбирается в браузерном Worker, после чего библиотека открывается без ожидания обработки всех треков внешними каталогами. Полной предварительной загрузки всех обложек, жанров и аудио при импорте нет.

## Текущее поведение

- Обложки и метаданные запрашиваются для видимых карточек и выбранных треков. Очередь сначала получает основные сведения, затем дополнительные жанры и теги.
- Очередь обложек допускает две одновременные партии по шесть треков; подробные сведения обрабатываются меньшими партиями по три после основных запросов. Сервер дополнительно ограничивает обращения к каждому источнику.
- Поиск полной записи запускается при включении трека. Это позволяет не проверять доступность аудио для всей библиотеки заранее.
- История аудитории исполнителей проверяется отдельной автоматической очередью в фоне. Она не блокирует открытие библиотеки.

Фильтр жанров использует уже полученные метаданные. Если жанр ещё не найден, трек не становится известным жанру просто из-за завершения импорта. Порядок и ограничения описаны в [жанрах и фильтрах](genre-filters.md), [источниках аудио](audio-sources.md) и [истории аудитории](audience-sources.md).

## Условная оценка времени

Оценка зависит от количества уникальных треков, альбомов и исполнителей, попаданий в кеш, числа обращений на трек, задержек сети, ответов источников и повторных попыток. Число событий прослушивания само по себе не определяет количество внешних запросов.

Для примера предположим, что для 10 000 уникальных треков нужен ровно один новый запрос к одному источнику, а запросы запускаются через постоянный интервал. Простое произведение количества на интервал даёт следующую оценку работы такой очереди:

| Интервал между запросами | Расчёт для 10 000 запросов |
| --- | --- |
| 180 мс | около 30 минут |
| 220 мс | около 37 минут |
| 1 050 мс | около 2 часов 55 минут |
| 3 100 мс | около 8 часов 37 минут |

Это условные расчёты, а не результаты замера архива и не обещание покрытия. Такие интервалы встречаются в настройках приложения, но не означают разрешение поставщика на соответствующую нагрузку. Один трек может потребовать несколько запросов и резервных поисков; общий альбом или исполнитель, наоборот, может позволить повторно использовать результат. Задержки, тайм-ауты и `429` увеличивают время. Независимые разрешённые очереди могут работать параллельно, поэтому времена разных источников не всегда складываются.

Дополнительные браузерные Worker ускоряют подходящую локальную обработку, но не отменяют сетевые ограничения. Увеличение числа серверных экземпляров также не даёт общей квоты: кеш и ограничители текущего API находятся в памяти отдельных экземпляров Vercel. Для устойчивой массовой обработки понадобятся общий кеш и согласованное управление частотой, с учётом правил каждого поставщика.

## Что потребовалось бы для полного предварительного обогащения

Потребовались бы возобновляемая очередь, устранение повторов по трекам, альбомам и исполнителям, контроль доступности источников, обработка `Retry-After` и сохранение разрешённых метаданных с датой проверки. Видимые карточки и запрос воспроизведения должны сохранять приоритет, чтобы длинная очередь не задерживала использование сайта.

Сохранять при этом нужно допустимые метаданные, ссылки и происхождение результата. Приложение не создаёт локальные файлы обложек или музыки: изображения и аудио получает браузер по внешним URL. У аудиоссылок может быть ограниченный срок действия, поэтому заранее найденный URL не гарантирует воспроизведение спустя годы. Обычный HTTP-кеш браузера и CDN определяется их настройками.

Даже полностью завершённая очередь не означает, что для каждой песни найден жанр или полная запись, а для каждого исполнителя - историческая аудитория. Отсутствующие данные должны оставаться неизвестными. Текущее развёртывание и ограничения кеша описаны в [инструкции по развёртыванию](deployment.md).
